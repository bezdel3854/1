# Railway: автономный paper trading

Подготовлено для развёртывания; действующий Railway-сервис этим проектом не создан.
Реальных ордеров нет, биржевые ключи не требуются.

1. Проект размещён в GitHub `bezdel3854/1`, ветка `bingx-paper-bot` (PR №1). Для деплоя выбрать эту ветку; основной `main` пока содержит исходный README.
2. Railway → New Project → Deploy from GitHub repo → выбрать репозиторий.
3. Добавить постоянный **Volume с mount path `/data`**. Не запускать без Volume: иначе после redeploy виртуальный счёт потеряется.
4. Переменные: `MODE=paper`, `DB_PATH=/data/paper.sqlite`, `PORT=8080`.
5. Только **1 replica**. Не использовать cron: worker непрерывный. Отключить serverless sleeping.
6. Для Volume задать `RAILWAY_RUN_UID=0`, если платформа требует UID владельца. Проверить доступ на запись `/data` в логах. См. актуальную документацию Railway по Volume permissions.
7. Deploy. Dockerfile обнаруживается автоматически. Начальная загрузка индикаторов может занять до 180 секунд. `/health` возвращает 200 после успешного цикла; 503 при ошибке или отсутствии успешных циклов более 120 секунд.
8. В логах должны быть строки `"mode": "paper"`, equity около 1000 и текущая метка времени. Это не подтверждает сделки или доходность.
9. Проверить перезапуск: equity/позиции и `last_signal` должны восстановиться из SQLite. Не удалять Volume при redeploy.

## Журнал и управление

- Полный журнал событий и закрытые сделки: `/data/paper.sqlite`, таблица `journal`. Состояние, сделки и cursor funding сохраняются в одной транзакции.
- Экспорт: `python -m bingx_bot.cli export --db /data/paper.sqlite --out /data/trades.csv` **при остановленном worker** (он держит single-writer lock).
- Мягкая остановка торговли: создать файл `/data/STOP`. На следующем успешном цикле бот закроет виртуальные позиции и запретит входы. При недоступном API действие ждёт свежих котировок.
- После удаления `/data/STOP` торговля может возобновиться, если не сработал лимит риска. Постоянная остановка по просадке 10% сохраняется; автоматического сброса нет.
- Остановка Railway/ SIGTERM сохраняет уже закоммиченный счёт. Виртуальные позиции остаются открытыми; после запуска выходы исполняются по первым свежим котировкам. Это риск паузы, а не непрерывное исполнение.
- Скопировать SQLite корректно через sqlite backup API, а не копировать только основной файл при работающем WAL. Внешнюю резервную копию делать по выбранному графику.
- Следить за диском: heartbeat записывается каждый цикл; настроить внешнюю ротацию/архивирование после остановки worker. Автоудаление финансового журнала не предусмотрено.
- Публичный домен необязателен. HTTP показывает только состояние здоровья; торговых маршрутов нет.

## Что ещё не проверено

Docker daemon в среде разработки отсутствовал. Docker build и минимальный запуск образа уже успешно прошли в GitHub Actions (run 40180071957). Работа сетевого worker и Volume именно в Railway пока не проверена; успешного облачного деплоя нет. Сервису нужен исходящий HTTPS-доступ к `open-api.bingx.com`. Недоступность биржи, свежести или корректности данных блокирует симуляцию; после пяти последовательных ошибок процесс завершается для контролируемого перезапуска.

## Конфигурация инфраструктуры

На 25.10.2026 Railway заменяет `railway.json` на IaC; новым сервисам старый формат недоступен. Поэтому основной шаблон — `.railway/railway.ts`. Старый пример оставлен только как `docs/railway.legacy.json`; корневого `railway.json` нет.

IaC-шаблон описывает worker, Volume 1 ГБ, переменные и healthcheck. Его применение не выполнялось: SDK/CLI Railway не установлен и аккаунт не подключён. Для ручного развёртывания выполнить шаги выше; Start Command `python -m bingx_bot.cli paper`, Healthcheck Path `/health`, timeout 180 секунд, Restart Policy On Failure с 5 попытками задать в интерфейсе. При использовании IaC проверить регион Volume, связать сервис с GitHub, установить SDK `railway`, выполнить `railway login`, `railway link`, `railway config plan`, затем применить просмотренный план. Не применять шаблон к проекту с посторонними сервисами.

## Новые исследовательские модели

`STRATEGY=regime_composite` либо `STRATEGY=consensus` выбирает общую экспериментальную систему. По умолчанию она только журналирует сигналы, без виртуальных входов. Весь список имён выводится `python -m bingx_bot.cli paper --help`. Для новой стратегии нужен новый `DB_PATH`, чтобы не смешивать историю и конфиги. Ни одна модель не прошла исследовательский фильтр; не менять параметры для обхода gate после просмотра результата.
